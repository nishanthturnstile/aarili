# Aarili

Boutique management portal with the merged Wave 0 Phase 0.1–0.3 foundations:
reproducible workspace, bilingual design system, local infrastructure and health,
protected owner access/recovery, shop isolation and a tested command/history
contract, exact money, durable jobs and restore fencing. Development is synthetic-only; business workflows and live activation
remain later scope. See the [foundation acceptance record](docs/agents/Phase_0_Closeout_Acceptance.md).
Read AGENTS.md and the product/architecture documents before implementing a selected issue.

Use this single local checkout for all development, switching between focused
topic branches. Do not create Git worktrees or extra feature checkouts. Follow
[the development workflow](docs/agents/Development_Workflow.md); each issue gets
its own GitHub branch/PR after its direct blockers have merged.

## Native Windows development

Use Node **24.21.0 LTS** and pnpm **12.11.2** on Windows/PowerShell. The exact
runtime is in .node-version; packageManager and engines reject version drift.
Install the pinned pnpm with `npm install --global pnpm@12.11.2` if needed.
Quote the checkout path when changing directories.

~~~powershell
pnpm install --frozen-lockfile
pnpm dev
~~~

The web listens at http://127.0.0.1:3000; the worker logs its ready state.
`pnpm dev:web` and `pnpm dev:worker` start them separately. Ctrl+C stops
development processes. The worker also supports graceful SIGINT/SIGTERM and
an IPC shutdown message; IPC is the automated graceful shutdown path on
Windows. Normal worker startup registers no demonstration consumers or schedules.
It uses the application database role to check the provisioned queue schema and
restore control. Foundation handlers are composed explicitly only by verification
and inspection commands. Web health uses a short-lived, bounded PostgreSQL connection.

The home page redirects to `/sign-in`; operational readiness remains at
`/api/healthz`. Configure server-only `DATABASE_URL` in
`apps/web/.env.local` using the **app_user** password generated by `pnpm infra:init`
(read it locally from ignored `infra/.local/user_password`). Use the URL shape
in `apps/web/.env.example`; never use admin/migration credentials. Start the
dedicated database with `pnpm infra:up`. Missing or unusable configuration
returns HTTP 503 from the health API while the sign-in page remains reachable.
Provide the worker's server-only process environment with its own `app_user`
`DATABASE_URL`; see `apps/worker/.env.example`. Worker configuration and reviewed
migrations are required before starting it.
All NEXT_PUBLIC_* variables are rejected in this increment. Server environment
validation is owned by platform, imported only at server entry points. Errors
do not print supplied configuration values. Only the light/dark appearance
preference is remembered locally; account and business state are not persisted.

## Checks and production entry points

~~~powershell
pnpm lint
pnpm knip
pnpm typecheck
pnpm test
pnpm test:negative
pnpm test:integration
pnpm build
pnpm smoke
# Runs all of the preceding checks:
pnpm verify
# Installs and verifies in a disposable temporary directory with spaces:
pnpm verify:clean
# Installs Linux dependencies and runs the same checks:
docker build --progress plain -f Dockerfile.verify -t aarili-verify:local .
# Runtime checks use the local Linux engine socket and disposable databases:
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aarili-verify:local
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aarili-verify:local pnpm test:ui
~~~

`pnpm format` uses only Biome. The root config intentionally excludes existing
planning documents and skills. Typecheck uses local TypeScript 7.0.2, generates
Next route helpers, checks tests and emits strict shared declarations. Negative
fixtures must actually fail with the expected diagnostics. The import checker
parses TypeScript and follows browser imports/re-exports, including aliases,
dynamic imports and require; it checks core/API restrictions before business
modules are added. Unsupported computed imports fail closed.

After building, `pnpm --filter @aarili/worker start` starts the compiled worker.
`pnpm --filter @aarili/web start` starts Next locally. The standalone server
for later image packaging is `apps/web/.next/standalone/apps/web/server.js`;
Next's standalone output also needs the generated .next/static directory
copied into its app directory to serve client assets. This ticket does not
deploy that output. Smoke verifies actual production HTTP and worker processes
on a free loopback port, then cleans up only those processes.

Docker Desktop uses its WSL2 Linux engine for verification. Normal app/install
commands stay on native Windows. Dockerfile.verify is a disposable verification
image with a digest-pinned Node base; .dockerignore excludes credentials,
Windows dependencies and generated outputs. Dedicated local infrastructure is
managed separately below; no cloud resources are provisioned. The image build
runs checks that need no Docker daemon; its default runtime command runs full
verification including real Testcontainers and production HTTP readiness.

## Dedicated synthetic local infrastructure

Docker Desktop supplies the Linux PostgreSQL and Garage S3 containers; Node,
pnpm and the application stay native on Windows. No second WSL daemon is needed.

~~~powershell
pnpm infra:init     # Once: generate ignored random credentials; refuses overwrite
pnpm infra:doctor   # Runtime/daemon/ports/reservations; no secret values
pnpm infra:roles    # Explicit privileged upgrade for retained synthetic volumes
pnpm infra:up       # Wait for health, then verify native SQL and signed S3 access
pnpm infra:check    # Repeat SQL/role/extension and S3 put/read/remove probes
pnpm infra:verify   # Synthetic persistence rehearsal across normal down/up
pnpm infra:down     # Stop/remove only Aarili containers/network; preserve volumes
~~~

The dedicated project is `aarili-local`. PostgreSQL uses
`127.0.0.1:55432`, database `aarili`, runtime `app_user` and migration `app_owner`.
Garage uses `http://127.0.0.1:53900`, region `garage`, path-style requests and
private bucket `aarili-synthetic`. Containers on `aarili-local_local` use
`postgres:5432` and `s3:3900`; native Windows uses the loopback endpoints.
Existing local-infra on port 5432 is preserved.

Optional port overrides belong in `infra/.env` copied from `infra/.env.example`,
or in `AARILI_PG_PORT` / `AARILI_S3_PORT` process variables (process wins).
Doctor checks Windows IPv4/IPv6 exclusions and listeners before startup.
See [the infrastructure guide and evidence](docs/agents/Issue_4_Local_Infrastructure_Evidence.md)
for credential handling, failure recovery and the separate explicit destructive reset.

## Synthetic owner access

Follow the [bootstrap runbook](docs/agents/Owner_Bootstrap_Runbook.md) before
using the owner screens. With local PostgreSQL running, on retained volumes run `pnpm infra:roles` explicitly,
then provide `MIGRATION_DATABASE_URL` only to the `pnpm db:migrate` process as
`app_owner`. The reviewed runner takes an advisory lock and checks applied SQL
hashes. Keep the web `DATABASE_URL` on `app_user`; never place migration/admin
credentials in the web or worker environment. Preserve retained volumes.

Use ignored `apps/web/.env.local` and the keys in
`apps/web/.env.example`: explicitly enable `AARILI_SYNTHETIC_AUTH`, use the exact
loopback `AUTH_ORIGIN`, independently generate `BETTER_AUTH_SECRET` and
`SETUP_TOKEN`, and select an absolute private `AUTH_CAPTURE_DIRECTORY` outside
the checkout. Restrict its Windows ACL to the developer account. The runbook
defines secret generation/handling; do not paste secrets into chat, logs or URLs.

| Screen | What to validate |
| --- | --- |
| `/setup` | One-time synthetic owner admission and private-code verification; resume the same pending identity if needed |
| `/sign-in` | Verified email/password sign-in and recoverable denial |
| `/owner` | Create the reserved shop once, retain it across restart and sign out |
| `/recovery`, `/reset-password` | Request a captured opaque reset code, set a 15–128-character password and return to sign-in |
| `/reauthenticate` | Confirm the current password after the five-minute recent-access window |
| `/connections` | Inspect the disabled Google state; real linking requires its separate activation checklist |

After verified shop completion, remove `SETUP_TOKEN` and restart the web process,
preserving the auth secret/runtime credential. Completion is permanent in that
database; restarting or re-adding a token does not reopen setup. Captures are
private filesystem files, not a web mailbox; remove them after the exercise.

The [recovery runbook](docs/agents/Owner_Recovery_Runbook.md) explains reset,
session revocation and recent authentication. The
[Google activation runbook](docs/agents/Owner_Google_Activation_Runbook.md)
separates simulated provider coverage from actual credentials, matching verified
identity, exact redirect/origin and approved real-provider smoke. Google remains
disabled unless separately enabled; no manually fetched Google access token is
needed for local validation. Production auth email still requires 0.3.2 suppression
guards and the domain/DNS/provider gates. Public signup remains closed.

## Package boundaries

apps/web mounts packages/api in one Node runtime route. packages/contracts
owns health, owner and command DTOs. The API's `client` export provides
browser-safe typed health/owner calls and wire validation. Synthetic command
clients are separate at `@aarili/api/command-fixture-client` and are forbidden
from application imports. No runtime environment mounts their endpoints or API
documentation. Route composition remains server-only.
packages/core holds framework-free command policies; packages/db supplies
transaction-bound repositories and shop context. packages/auth composes
server-only sessions, owner access and membership checks. packages/platform
owns server-only environment validation and operational database readiness.
packages/ui owns the canonical globals.css, Tailwind v4 tokens, locally served
Noto Sans/Noto Sans Tamil and Base UI controls. See the
[design-system guide and acceptance evidence](docs/agents/Issue_3_Design_System_Evidence.md)
for the actual shadcn preset, generator comparison and component-add procedure.

## Selected themes and browser validation

Run `pnpm dev:web`, then open the owner sign-in screen. The selected Current
light/dark themes use Noto Sans and Noto Sans Tamil. Appearance is remembered;
every page starts in English and switches to Tamil only on explicit selection.
The gallery and development landing UI are removed in all environments.
Change colours, typography, radii, density and motion in
`packages/ui/src/globals.css`; app CSS only imports that file. See the active
[design-system specification](docs/aarili-design-system.md).

~~~powershell
pnpm tokens
pnpm exec playwright install chromium
pnpm test:ui
~~~

Browser tests start and stop a disposable Testcontainers PostgreSQL instance
and their own dev server on port 3103. Chromium must
be installed separately on each host; never copy browser or node_modules
binaries between Windows and Linux. Captures in
`docs/agents/design-cleanup/captures` are selected-theme review evidence; older
captures remain historical evidence, not cross-platform pixel-perfect goldens.
`pnpm verify` runs the non-browser checks; run
`pnpm test:ui` separately when controls or tokens change. Use
`pnpm test:ui --grep 'operational readiness'` for health/removed-route tests only. Both `pnpm verify` and the
browser wrapper require Docker Desktop with the Linux engine running.

See [the database health guide and acceptance evidence](docs/agents/Issue_5_Database_Health_Evidence.md)
for fixture lifecycle, timeout/failure tests, observed random endpoints and

## CI and dependency policy

`.github/workflows/verify.yml` runs Linux scaffold verification, the implemented
phone/tablet/desktop browser/axe suite and a dependency audit on branch pushes
and pull requests to main. Each job uses exact Node/pnpm pins, a frozen install
and Actions pinned to full commit SHAs. PostgreSQL remains disposable through
Testcontainers; no development or production database credentials are supplied.

production promotion or deployment occurs.

schema-defined 200 or sanitized 503 with `Cache-Control: no-store`. Unknown API routes and unsupported
methods return a shared error. Merged issue #12 adds protected synthetic owner setup,
opaque-code verification, verified database sessions and initial shop creation.

transport or production activation is enabled.

context guard. On a retained local volume, run `pnpm infra:roles` explicitly
before `pnpm db:migrate` with the separate app_owner migration configuration;
do not reset the volume. Fresh volumes provision the roles during initialization.
